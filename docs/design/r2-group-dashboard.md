## 2. Decisions proposed (defaults, change any)

1. **Period = calendar month**, data as at month end; quarters and years are derived. One upload per subsidiary per month; a corrected file is a new version.
2. **A valid upload is accepted automatically** and becomes the version in use; an upload with errors is rejected with its error report and changes nothing. Sirius HR doesn't approve uploads (not in the BRD); anomalies are handled by flags.
3. **Placeholder field template (A3)**, all configurable: employee ID\*, full name\*, department\*, designation\*, grade\*, gross monthly salary\*, currency\*, date of joining\*, date of birth\*, gender\*, nationality, employment status\* (active / on leave / left), leaving date, cost centre. Basic salary and allowances optional.
4. **Anomaly rules (placeholders, thresholds configurable):** `ANM-01` employee missing vs prior period without a leaving date; `ANM-02` grade changed; `ANM-03` gross salary changed by more than 20%; `ANM-04` salary unchanged for 12 months then changed (BRD example); `ANM-05` salary differs from the increment approved in the Increment Portal (Figma flag detail); `ANM-06` salary outside its grade band; `ANM-07` same employee ID in two subsidiaries. Entity-level warnings: headcount or payroll moved by more than 10% vs prior period.
5. **Flag owner** defaults to the subsidiary user who uploaded; Sirius HR can reassign. Subsidiary HR and Sirius HR can move a flag; resolving needs a note.
6. **Reminders** reuse the S7 triggers: `upload_due` (subsidiary hasn't uploaded N days after month end, default 5) and `flag_open` (flag open more than N days, default 5).
7. **Scheduled reports** are generated by the worker and kept in the portal's report archive; recipients get an in-app notification and an email with a link (never the file attached: pay data stays behind sign-in). The same mechanism gives RP-01 weekly and RP-02 monthly (R1 gap).
8. **Executives** see D8 and RP-06/07 (aggregates only, no individual pay or names). **IHC** gets the PDFs from Sirius HR; no IHC login (project rule).
9. **Salary stays encrypted per record** (ADR-008). Dashboards read per-period aggregates (by entity, department, grade, gender, age band) computed by the worker when a version is accepted, so D5/D6 load in < 3 s without decrypting thousands of rows per view (NFR-PERF-01). New ADR-015.

## 3. Data model (new schema `groupdata`, all entity-scoped with FORCE RLS)

| Table                               | Purpose                                                                                                                                                    |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `field_template` / `template_field` | Versioned template: key, label (en/ar), type (text, date, decimal, enum), mandatory, format, allowed values, Palm HR field, order                          |
| `upload`                            | `UP-NNNN`, entity, period, version, status (`validating`, `rejected`, `accepted`, `superseded`), file (object store, scanned), row counts, uploader, times |
| `upload_issue`                      | Row, column, code, message key (validation errors and warnings)                                                                                            |
| `employee_snapshot`                 | One row per employee per upload version: template values (typed columns for the core fields + `extra` jsonb), salary encrypted; partitioned by period      |
| `period_version`                    | Which upload is in use for (entity, period): the canonical pointer (R2-04)                                                                                 |
| `record_change`                     | Per employee per new version: field, before, after (R2-13; sensitive values encrypted)                                                                     |
| `period_metrics`                    | Aggregates per entity × period × dimension, written by the worker                                                                                          |
| `anomaly_rule`                      | Code, kind, threshold, enabled, severity (configuration)                                                                                                   |
| `anomaly_flag`                      | `AN-NNNN`, rule, entity, period, employee, upload, previous → current (display values), owner, status, resolution note                                     |
| `report_run`                        | Scheduled / on-demand report files (RP-01 … RP-08): type, period, format, object key, created by, recipients                                               |

`core.employee` stays the current master: the latest accepted current-period version updates it, so the Increment Portal always offers today's employees and salaries.
