# ADR-015: Group employee data: uploads, versions, aggregates and anomaly flags

- **Status:** Accepted (2026-10-19, R2 design approved by the product owner); the field list (BRD A3), Palm HR fields (A7) and rule thresholds need Sirius HR's sign-off
- **Requirements:** R2-01 … R2-04, R2-08 … R2-14, NFR-PERF-01, NFR-DQ-01, NFR-CFG-01, NFR-SEC-01, NFR-PRIV-01
- **Related:** ADR-002 (RLS), ADR-008 (field encryption), ADR-010 (file storage and scanning), ADR-011 (audit, notifications), ADR-014 (reminders), migrations core `0013_group_data`, `0014_data_quality`; `packages/db/src/group-data.ts`, `data-quality.ts`, `approved-increments.ts`; `apps/api/src/modules/group-data/*`; design `docs/design/r2-group-dashboard.md`

## Context

Subsidiaries upload their employee data each month against a standard field template that Sirius HR hasn't agreed yet (A3). The group needs one record per employee per month (R2-04) with every earlier version kept, a comparison with the previous month (R2-09), configurable anomaly rules (R2-10) and a resolution workflow (R2-11), dashboards under 3 s (NFR-PERF-01), and a raw extract (R2-08) — while salaries stay encrypted per record (ADR-008) and each subsidiary sees only its own data (R2-12).

## Decision

1. **Configuration, not code.** The field template is versioned rows (`groupdata.field_template`, `template_field`): label (en/ar), type (text, date, decimal, list), required, allowed values, Palm HR field. A placeholder version 1 ships with 15 core fields. Admins publish a new version; core fields keep their key and type and can't be removed, and the fields the dashboards need stay required. Grade bands (`grade_band`, Figma values) and anomaly rules (`anomaly_rule`, ANM-01 … ANM-09) are rows too. These tables are readable by everyone and writable only in group scope (RLS), on top of the API's `template:configure`.
2. **A month is a calendar month**, data as at its end. An upload is **all or nothing**: a file with any error is recorded as `rejected` with its problems (row, field, code — never the cell's value) and changes nothing; a valid file becomes **the next version** (`version` = previous + 1 per subsidiary and month, under an advisory lock) and the version in use (`period_version`). The version it replaces becomes `superseded`; its open flags are closed with `resolved_reason = 'superseded'`. Uploading the same file as the version in use is refused (409), which also makes a double submit harmless. Sirius HR doesn't approve uploads (not in the BRD): anomalies are handled by flags.
3. **Records are append-only snapshots.** `employee_snapshot` holds one row per employee per accepted upload (typed core columns + `extra` jsonb for admin fields), **partitioned by period** (yearly partitions 2024–2028 and a default), with an append-only trigger. Gross and basic salary are AES-GCM encrypted with the row ID as associated data (ADR-008). The newest month in use refreshes `core.employee` (the Increment Portal's employee list): new employees are added, missing ones made inactive.
4. **Files are read defensively before anything else.** Size ≤ 5 MB; type from content (Excel by magic bytes; otherwise strict UTF-8 text named `.csv`); malware scan; the zip central directory is inspected before Excel opens a workbook (macros, > 2,000 entries, > 60 MB uncompressed or a ratio > 200 are refused); formulas are reported and never evaluated; ≤ 10,000 rows; CSV must be valid UTF-8 without NUL. The original file is kept in private object storage (`group-uploads/{entity}/{id}`) and downloadable, audited.
5. **Comparison and rules run in the API, as pure functions** (`compare.ts`) on the decrypted records of this upload and the previous month in use, with exact decimal arithmetic (rounded only for display): missing employees, grade changes, salary change beyond a %, change after N stable months, salary off the increment approved in R1 (latest decision per employee, new salary computed with the R1 money rules), outside the grade band in its currency, the same employee ID in another subsidiary this month (`groupdata.employee_numbers_elsewhere`, a `SECURITY DEFINER` function that answers only "which of these IDs", then restores the caller's scope), and subsidiary-level headcount and payroll moves (payroll compared per currency, never summed across currencies). Flags store **display values only**, encrypted (`anomaly_flag.detail`).
6. **Dashboards read per-period aggregates, not salaries.** Each accepted version writes `period_summary` (per department: headcount, joiners, leavers, gender, age bands, per grade headcount and payroll per currency). D5/D6/D8 add these rows, so they never decrypt thousands of salaries per view (NFR-PERF-01). The aggregates hold totals, not individual pay; they are entity-scoped like everything else.
7. **Flags have an owner, a status and a note.** The uploader owns the flags of their upload; Sirius HR or the subsidiary can reassign (to someone who uploaded that subsidiary's data, a current owner, or themselves), move it open → in progress → resolved (a note is required to resolve; the note is encrypted, the audit records only that one was written), and Sirius HR can send a reminder. Owners are told of changes made by others. Reminders: `upload_due` (last month not uploaded N days after month end, to the subsidiary's HR users) and `flag_open` (open more than N days, to the owner), queued by `notify.queue_group_reminders()` for the worker role only, once each (ADR-014's pattern).
8. **Everything is audited** (R2-13): template published, upload rejected / accepted (version, rows, flags, the version it replaced), original file downloaded, raw extract (format, rows, filters), flag raised / updated / reminded, rule updated. A record's history shows each field that changed between versions.

## Alternatives considered

- **Sirius HR approves each upload before it is used:** not in the BRD; slows the month-end; flags give the same control on what matters.
- **Overwrite the month's records on re-upload:** loses history (R2-04 asks for prior versions retained).
- **Store salaries in clear for aggregation, or compute dashboards on the fly:** the first breaks ADR-008; the second can't meet < 3 s at group scale without decrypting every row per view.
- **Anomaly rules in SQL:** harder to test with worked examples and to keep in exact decimals; the API already has the decrypted records at upload time.

## Consequences

- Corrections are a new upload of the whole month: simple to reason about, and every version stays.
- Period partitions must be added before 2029 (a default partition catches anything else; DEPLOYMENT.md).
- The placeholder template and rules must be replaced with Sirius HR's before UAT; changing the template later doesn't affect accepted uploads (each records its template version).
- Grade bands are seeded from Figma and not yet editable on screen; until they are, changes are a reviewed migration.
