# ADR-011: Audit trail, status history and notifications

- **Status:** Accepted (2026-10-14); email provider TBC with Sirius IT (A6)
- **Requirements:** R1-07 (submit to Sirius HR, notify), R1-13 (notifications, reminders), R1-15 / R2-13 / NFR-AUD-01 (audit trail), R1-11 / R1-12 (TAT and back-and-forth need status history), NFR-PRIV-01, NFR-SEC-01
- **Related:** ADR-002 (Row-Level Security), ADR-010 (evidence downloads), migration `0005_submission_audit_notifications`, `packages/db/src/audit.ts`, `packages/db/src/notifications.ts`

## Context

Submitting a request (S4a) is the first state change Sirius cares about. Three things have to happen when it does: the status history used for TAT gets an entry, the action is audited, and both sides are told. The project rules require the audit log to be append-only "enforced with DB permissions, not just code", and exports and downloads to be audited too. The email provider isn't known yet (A6), and no worker exists.

Sirius users (reviewers, admins) aren't stored in the database; their roles come from the identity provider on each request. So "notify the reviewers" can't fan out to a list of user IDs.

## Decision

1. **One transaction per action.** Submit locks the draft, checks the version, updates the status, writes a `status_event`, an `audit_log` row and the notifications (plus their email outbox rows) together. Either all of it happens or none.
2. **Append-only by grants and a trigger.** The app role has `SELECT, INSERT` only on `audit.audit_log` and `increments.status_event`. A statement-level trigger (`audit.refuse_change()`) refuses `UPDATE`, `DELETE` and `TRUNCATE` for every role, the table owner included. Tests prove both.
3. **The audit trail is protected by RLS too.** A row can only be inserted with `actor` = the session user and an entity the actor can access, so nobody can write entries in someone else's name. Reading it is limited to group scope (and `audit:read` in the API, when the audit screen lands).
4. **What is audited:** creating, saving, submitting and discarding requests; adding and removing employees; uploading, removing and **downloading** evidence. `details` holds identifiers and counts only — never salaries, justifications or file contents (NFR-PRIV-01).
5. **Notifications are stored as `kind` + `params`**, not as text, so each reader sees them in their language (i18n rule) and wording can change without a migration. `params` holds display values only (reference, employee count, entity code, actor name).
6. **Two kinds of recipient:** one user (`recipient_user_id`), or everyone holding a role (`recipient_role`, e.g. the reviewer role). Role-addressed rows are readable only in group scope; the API matches them against the caller's roles from the token. Read state is per user (`notification_read`), so each reviewer has their own unread count.
7. **Email via an outbox.** Every notification gets a `notify.email_outbox` row in the same transaction. The app role can only insert there. A worker with its own database role will read, send and mark rows once the email provider is approved (S4b). Until then rows wait; nothing is lost.
8. **IDs are generated by the API** for notifications, because PostgreSQL checks `INSERT … RETURNING` against the SELECT policy, and the submitter can't read a role-addressed row.

## Alternatives

- **Audit via database triggers on every business table.** Catches everything, including changes made outside the API, but sees only rows (not intent: "downloaded", "submitted"), can't record reads, and would need the user ID passed into every trigger. Rejected for now; may be added later as a second line for direct database changes.
- **A separate audit database or an external log service.** Stronger separation, but adds infrastructure that A6 hasn't approved and loses the same-transaction guarantee. Revisit if Sirius requires tamper-evidence (e.g. hash chaining) or offsite retention.
- **Sending email directly from the API request.** Simpler, but a slow or failing provider would fail or slow the submit, and a crash after commit would lose the email. Rejected.
- **Fanning role notifications out to user rows.** Needs a directory of Sirius users, which we don't have (roles live in Entra ID). Rejected; revisit if the IdP integration provides group membership.

## Consequences

- The audit log grows with every action, including downloads. It should be partitioned by month once volumes are known (ADR-004), and archived after the retention period (proposal: 7 years; Q10).
- Corrections are made by new entries, never by editing old ones. A mistaken audit row can only be fixed by a migration run by the database owner after disabling the trigger, which is itself a reviewed change.
- Until the email worker exists, users see notifications only in the portal.
- `status_event` is the source for TAT and back-and-forth (R1-11, R1-12); how time is counted (calendar vs business hours) is still ADR-006.
